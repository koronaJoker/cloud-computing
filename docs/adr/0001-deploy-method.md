# ADR-0001. Обновление приложения через Git pull

**Статус:** принято
**Дата:** 2026-10-04

## Контекст

TimeCapsule развёрнут на EC2-сервере с nginx, PHP и PostgreSQL. Необходимо выбрать простой способ доставки новых версий приложения на сервер.

Проект является учебным и разворачивается на одном сервере. Поэтому нет необходимости сразу использовать сложную CI/CD-инфраструктуру. При этом исходный код уже хранится в Git-репозитории, поэтому желательно использовать Git для получения обновлений на сервер.

## Решение

Для доставки новых версий приложения на сервер используем ручной `git pull`.

После подключения к серверу по SSH переходим в каталог приложения и выполняем `git pull`. Сервер получает последние изменения из удалённого репозитория, после чего приложение использует обновлённый код.

Такой способ выбран из-за простоты и того, что он хорошо подходит для небольшого учебного проекта с одним сервером.

## Рассмотренные альтернативы

**1. Копирование файлов через `scp`.**
Можно было бы копировать изменённые файлы с локального компьютера на сервер с помощью `scp`. Этот способ не требует Git на сервере, но при каждом обновлении пришлось бы самостоятельно выбирать и копировать файлы. Это повышает вероятность забыть какой-либо файл и не использует преимущества истории версий Git.

**2. `git pull` вручную на сервере.**
Выбранный вариант. Сервер уже связан с Git-репозиторием, поэтому для получения новой версии достаточно подключиться по SSH и выполнить `git pull`. Способ простой, понятный и не требует дополнительной инфраструктуры.

**3. Скрипт `deploy.sh`.**
Такой вариант позволил бы автоматизировать последовательность команд деплоя. Однако для текущего небольшого учебного проекта отдельный скрипт не нужен: ручного `git pull` достаточно, а добавление скрипта увеличило бы количество файлов и необходимость их поддержки.

## Последствия

**Плюсы:**

* простой процесс обновления приложения;
* используется существующий Git-репозиторий;
* сохраняется история изменений и версии кода;
* не требуется отдельная CI/CD-система;
* легко понять и повторить процесс деплоя.

**Минусы и риски:**

* обновление выполняется вручную;
* можно забыть выполнить дополнительные действия, необходимые после изменения кода, например миграции базы данных;
* при неправильном состоянии рабочей директории `git pull` может завершиться конфликтом;
* нет автоматического деплоя после `git push`.

Для небольшого учебного проекта эти ограничения приемлемы. При увеличении проекта или появлении нескольких серверов процесс можно будет заменить на автоматизированный CI/CD-деплой.
