    Что такое User data и когда выполняется этот скрипт? Выполнится ли он повторно после перезагрузки экземпляра?   

**User data** — это скрипт или данные, которые передаются облачному экземпляру при создании. Служба cloud-init внутри ОС читает их и выполняет автоматически, без ручного входа на сервер. Используется для начальной настройки: установка пакетов, запуск сервисов и т.д.

**После перезагрузки:** нет, повторно не выполнится. По умолчанию **user data** запускается только при первом старте. Чтобы он выполнялся при каждом запуске, нужно специально настроить cloud-init 

При этом nginx после перезагрузки всё равно запустится, потому что `systemctl enable` включил его автозапуск. То есть результат скрипта сохраняется, а сам скрипт заново не запускается.

    Почему для входа на экземпляр EC2 используется ключ, а не пароль?

Потому что ключи безопаснее паролей:

- Нельзя подобрать перебором. Пароль можно угадать или взломать брутфорсом, а приватный ключ (2048+ бит) практически невозможно. Экземпляр с публичным IP постоянно сканируют боты, и пароли быстро подбирались бы.
- Секрет не передаётся по сети. При входе приватный ключ остаётся у вас: вы лишь доказываете, что владеете им (подпись), а на сервере хранится только публичный ключ.
- Нет слабых паролей. Ключ генерируется автоматически, его нельзя сделать «123456» или использовать повторно на других сервисах.
- Автоматизация. Ключи удобны для скриптов и инструментов (Ansible, CI/CD): не нужно хранить и вводить пароль.

scp (secure copy) копирует файлы между вашим компьютером и удалённым сервером по защищённому каналу. Синтаксис: scp [откуда] [куда], где удалённый путь записывается как user@host:путь.

**Чем похожа на ssh:**

- работает поверх протокола SSH (тот же порт 22, то же шифрование);
использует ту же аутентификацию: ключ через -i, тот же user@host;
использует тот же файл known_hosts для проверки сервера.

- **Отличие**: ssh открывает удалённую консоль для выполнения команд, а scp только передаёт файлы и завершается.

    Почему публичный репозиторий безопасен

Публичным является код приложения, но не секреты:

    GitHub
    ├── исходный код ✅ публичный
    ├── composer.json ✅ публичный
    ├── .env.example ✅ публичный
    └── .env ❌ не публикуется

На сервере находится настоящий .env:

    EC2
    └── /var/www/timecapsule/.env
        ├── DB_USERNAME
        └── DB_PASSWORD

Таким образом, даже если кто-то увидит весь код на GitHub, он не получит пароль от базы данных.

публичный репозиторий безопасен только при условии, что секреты нигде не закоммичены — ни в .env, ни в исходном коде, ни в истории Git.

## Задание 12. Обновление приложения

![alt text](images/image-25.png)

1. Что может увидеть посетитель во время git pull?
В зависимости от того, какие именно файлы обновляются в данный момент, пользователь может столкнуться со следующими неприятными эффектами:

Ошибка 500 (Internal Server Error): Это самый частый сценарий. Например, Git обновил контроллер, который вызывает новый метод, но файл с представлением (view) или новая миграция еще не обновились. Либо PHP начал компилировать файлы в момент, когда они еще не до конца записались на диск.

Ошибки синтаксиса или «белый экран смерти»: Если PHP-скрипт прочитан веб-сервером ровно в тот момент, когда Git перезаписывает его (файл на доли секунды оказывается обрезаным или пустым).

Сломанный интерфейс (CSS/JS): Если обновился HTML-код (шаблон), а новые файлы стилей или скриптов еще не подтянулись, или наоборот. Браузер попытается загрузить несуществующие ассеты.

2. Что случится с сайтом, если не выполнить composer install?
Если в вашем коммите изменились зависимости (файлы composer.json или composer.lock), а вы забыли запустить composer install, сайт практически гарантированно упадет:

Ошибка Class ... not found: Новый код проекта может требовать сторонние библиотеки или новые классы, которые прописаны в автозагрузщике (autoload), но физически папки vendor/ для них еще нет или она старая.

Мгновенный сбой при первом же запросе, использующем новый функционал, со стандартной страницей ошибки 500.

Если же в коммите менялся только ваш собственный код (без изменения зависимостей в composer.json), то сайт может продолжить работать, но пренебрегать проверкой зависимостей все равно опасно.

### Как делать правильно и избежать проблем?

**1. Режим обслуживания (Maintenance Mode):**
Перед началом обновления сайт переводят в режим заглушки, выполняют все команды, а затем возвращают обратно.

**2. Атомарный деплой (Zero-Downtime Deployment):**
Профессиональные инструменты деплоя (например, Deployer, Envoyer или GitHub Actions) загружают и готовят новую версию кода в абсолютно чистой папке рядом, полностью выполняют composer install, сборку фронтенда и миграции, а в самый последний момент одной ссылкой (symlink) переключают веб-сервер на новый код. Для посетителей переход происходит мгновенно и незаметно.

# Контрольные вопросы

1. **Запрос от браузера до БД:**
   Браузер → **Nginx** → приложение на сервере → **PHP** → **PostgreSQL**.
   **Пример:** пользователь открывает `/users` → PHP получает данные из PostgreSQL → возвращает страницу.

2. **Почему сервер только скачивает код:**
   Сервер имеет доступ **только на чтение** к репозиторию. Это безопаснее, потому что сервер не может случайно изменить или удалить исходный код.
   **Пример:** `git pull` работает, а `git push` — нет.

3. **Что будет с файлами при удалении EC2:**
   Если файлы хранятся на **EBS**, они обычно сохраняются при удалении EC2, если том не удаляется вместе с экземпляром. Если файлы были только на локальном временном хранилище — они пропадут.
   **Пример:** EBS можно подключить к новому EC2 и получить файлы обратно.

4. **Связь с CI/CD:**
   `deploy.sh` выполняет те же основные действия: **получить код → установить зависимости → собрать/запустить приложение → проверить результат**.
   Не хватает автоматического запуска по `git push`, тестов, логирования и автоматического отката при ошибке.
   **Пример:** GitHub Actions может сам запустить `deploy.sh` после `git push`.
